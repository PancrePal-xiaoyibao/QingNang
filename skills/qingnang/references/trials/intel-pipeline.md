# 试验情报流水线（订阅推送型）

> **来源**：改进后并入自社区 skill `opencare-skillhub/clinicaltrials-intel-skill`（Apache-2.0）。
> **改动**：抽取其「阶段分离」的核心契约思想，改写为**给 Agent 的编排指引**；移除了 TG / GeWe / 飞书 / FastGPT 的具体接入细节（那些是运营系统的事，不属于本包）。
> **许可**：Apache-2.0，见 `references/SOURCES.md`。

---

## 什么时候用

用户要**持续跟踪**某类试验（而不是查一次）。例如：
- 「帮我盯着胰腺癌新登记的试验，每周给我一份」
- 「有新药进入三期就告诉我」

**与单次检索的区别**：单次检索是「问了才查」；情报流水线是「定期跑 + 有变化才提示」。

---

## 核心契约：**两阶段必须分离**

这是上游 skill 最有价值的设计，本包保留：

```
阶段 1 · 落地（只负责抓 + 存）
   抓取 → 结构化 → 落到本地文件
   产出：每条试验一个 JSON，带 sync_status 字段

阶段 2 · 消费（只负责读 + 推）
   读阶段 1 的产出 → 生成给用户的简报
```

**为什么必须分离**：

| 反面做法 | 后果 |
|---|---|
| 「抓到一条就推一条」 | 网络抖动 → 用户收到重复或半截消息；失败难重试 |
| 抓取与推送混在一个循环 | 推送失败会污染抓取状态，两者互相拖累 |
| 无中间落盘 | 重启即丢失进度，无法断点续传 |

**正确做法**：阶段 1 批量落地完成，阶段 2 才消费。**阶段 1 失败不影响已落地的部分。**

---

## 三条关键契约（改任何实现前必须理解）

| # | 契约 | 说明 |
|---|---|---|
| **C1** | **`sync_status` 字段是阶段间的隐式契约** | `pending` = 待处理，`processed` = 已消费。**改动它 = 改动两阶段的接口**，必须同步改两侧。 |
| **C2** | **登记号是去重唯一键** | `NCT\d{8}`（CT.gov）/ `ChiCTR\d{8,}`。从内容提取，**不依赖文件名**。文件名会变，登记号不会。 |
| **C3** | **去重按登记号 + 采集日期**，不按标题 | 标题会被申办方修改，导致同一条试验被当成两条。 |

## 青囊附加约束

上游面向运营，本包面向病友，加三条：

| # | 约束 |
|---|---|
| **I1** | **推送内容必须带采集时间**：「截至 2026-10-14，新增 3 项」 |
| **I2** | **不做「你应该关注这个」的判断**：只陈述新增了什么，指向官方链接 |
| **I3** | **不做自动加入建议**：「可以入组」这类话**永远不说**（触发红线 M1） |

## 最小可跑的编排（给 Agent 的伪代码）

```
# 阶段 1：落地
for 关键词 in 用户设的跟踪词:
    结果 = qingnang_trial.search(关键词, 带采集日期)
    for t in 结果:
        if 登记号 not in 已存:
            存(t, sync_status="pending")

# 阶段 2：消费
新增 = 读出所有 sync_status=="pending"
if 新增:
    简报 = 组装(新增, 带采集时间, 带登记号, 带官方链接)
    输出(简报)
    标记这些为 "processed"
```

> **Agent 的约束**：上面是**编排思路**，不是让你写一个长期驻留的守护进程。青囊不引入常驻服务（见 `AGENTS.md` §5：不引入服务端 / 云依赖）。
> 实际执行方式是：**用户来了就跑一次阶段 1 + 阶段 2**，或由用户自己挂 cron 调本包脚本。
